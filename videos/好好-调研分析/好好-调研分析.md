# 好好\-调研分析

# 调研目的

据2020年第七次人口普查数据，我国已进入老龄化社会；根据2020年人口抽样调查数据，我国已进入中度老龄化社会，老龄人口数量为银发产品的出现提供人口基础。

根据2022年卫健委发布的“十四五”健康老龄化规划，我国78%以上的老年人至少患有一种以上慢性病，失能老年人数量将持续增加。根据世界卫生组织2023年发布的Medication without harm，用药错误导致全球医疗保健可避免成本总额的9%，占全球总医疗支出的0\.7%，据估计用药错误的花费高达420亿美元。

因此，本文适应老龄化社会发展大趋势，以减少老龄慢病患者用药错误带来伤害的负面影响，锚定用药管理赛道，旨在提出一款帮助老龄慢病患者正确、规范、及时用药的适老化产品。

需注意，本产品特针对开药处方、处方转录、发药过程无错误，慢病患者自身存在用药依从性差、不及时、不规律问题而导致的用药错误现象。

# 行业数据

因本产品针对的是需长期用药的老年人，因此将用户分析暂且定为60岁及以上的老龄人口。

本节通过人口统计与互联网使用数据，明确用药管理产品面向人群基础、老年群体数字使用限制以及后续应重点验证哪些用户需求。

**数据说明：**本节将60岁及以上人口称为老年人口，人口调查数据包含2020年第七次人口普查数据、2025年人口抽样调查数据和2025年12月CNNIC互联网调查数据，不视为同一次调查结果。

## **老年人口互联网使用规模**

截至2025年12月，我国网民规模为11\.25亿人，60岁及以上网民占全部网民的15\.4%，据此计算：

60岁及以上网民规模 ≈ 11\.25亿人 × 15\.4% = 1\.7325亿人，约1\.73亿人。

数据来源：[CNNIC《第57次中国互联网络发展状况统计报告》](https://www.cnnic.cn/NMediaFile/2026/0304/MAIN1772588317069TUXN3827X8.pdf)，第1页、第18页。

分析：该结果表明，老年群体已存在一定规模的互联网使用者，具备探索数字服务的触达基础，但老年网民规模不等于养老数字产品用户使用数，也不等于能够独立安装、注册并长期使用产品的人，也不等于存在特定养老需求或愿意付费的人，因此1\.73亿并不等于目标市场规模，还需进一步明确存在用药管理需求的老年人使用以及付费意愿强度。

## 使用障碍

#### （1）非网民的使用障碍

截至2025年12月，我国6岁及以上非网民规模为2\.16亿人，其中60岁及以上人群占53\.6%。6岁及以上非网民整体中，因“不懂电脑/网络”而不上网的比例为47\.9%，因“不懂拼音等文化程度限制”而不上网的比例为30\.2%。

来源：[CNNIC报告，第16页。](https://www.cnnic.cn/NMediaFile/2026/0304/MAIN1772588317069TUXN3827X8.pdf)

分析：若目标服务需覆盖未上网老人，应调查其亲属、社区人员等现有协助渠道，区分不会安装、注册受阻或接受服务过程中需要帮助等环节。明确是否需要设置代操作功能、子女端或语音朗读功能，还应验证老人意愿、协助者可用性，不能直接由非网民占比直接决定。

#### （2）老年网民的数字技能

报告显示，60岁及以上网民中，至少熟练掌握任意一种受调查数字素养与技能的比例为20\.3%，20—29岁网民的对应比例为80\.3%。但不能据此认为只有20\.3%的老年网民能够顺利使用养老app。

来源：[CNNIC报告](https://www.cnnic.cn/NMediaFile/2026/0304/MAIN1772588317069TUXN3827X8.pdf)，正文第22页（PDF第30页）。

**分析：**为获得真实能够顺利使用养老app人群基数，应将家中有具备数字素养与技能、可对老人进行培训的家庭户考虑其中。同时，需要考虑可读性、任务理解、操作反馈或错误操作恢复以及教学简易性。初步原型可尝试清晰标签、选择代替人为输入、返回与撤销操作以及语音和亲属协助功能，通过任务完成率、求助点位、误操作与恢复情况验证问题点与效果。

同时，慢病患者用药场景各不相同，并非所有慢病患者都需要线上产品帮助用药管理，因此需要对不同用药场景进行分类，主要分为以下四种：慢病患者独自管理药物；患者与家属共同管理；家人代为管理；重病或身体功能受限患者由专业人士或机构代为管理。其中最后一类人群风险较高，通常无法靠单一线上产品解决问题，因此主要以前三类作为目标人群与访谈对象。

## 用药依从性影响因素

**定义：**用药依从性是患者实际用药行为与其和医疗专业人员共同确定的治疗建议相一致的程度，包括是否开始治疗、服药剂量、时间、频次以及能否持续执行。

**说明：**因用药依从性定义对象为患者本身，因此在该部分针对用药依从性元素分析也主要针对老龄慢病患者本人，不对临床医师、非正式照护者等其他参与角色进行分析。

**针对用药管理产品启发：**

用药管理App应采用同样的任务导向原则，但首页任务需要进一步收敛。首页应重点展示：

- 今日待服药物

- 下一次服药时间

- 已服、漏服和待确认状态

- 补服、跳过、服药异常等处理入口

- 联系家属或专业人员的紧急入口

药品资讯、健康文章、平台资源数量、地图、合作机构展示和商城推荐都不需要占据首页核心位置。用药管理属于高频且具有安全要求的任务，首页首先要保证老人能够快速看到“现在吃什么、吃多少、是否已经吃过以及出现问题怎么办”。

地图不是核心功能，无需进入一级导航；

家属端应能查看老人是否按时服药，但不能替代老人端的任务确认和异常反馈。

对比：与爱牵挂的“智能终端\+云平台”模式相比，东软智慧养老平台模式更多，涉及门户网站、手机app、公众号与小程序，同时东软增加了志愿者端、从业人员端与政府管理端，服务提供方更加多元。在产品使用上，爱牵挂主要通过依靠智能设备帮助老年人智慧养老，如智能手表、感应器、检测仪，而东软则更注重满足服务型消费需求，如商城、养老服务、护理服务、家务协助、陪伴聊天等。但并不代表爱牵挂只提供硬件，东软只提供软件，爱牵挂可通过硬件提供与售后一体化流程实现“设备\+情绪”康养，东软也可以在其商城售卖智能设备用于健康监测，但具体呈现效果如何需要进一步明确。

结论：两个案例都提示我们，在后续确定产品方向时，应围绕具体场景明确实际受益方、服务提供方、app操作者和费用支付者，再制作合理的操作入口与协作机制，不能只将能够熟练使用智能手机的老年群体列入目标人群范围。

# 功能重点总结

## 产品定位与设计前提

产品面向需要长期服用一种或多种药物的居家老人，覆盖老人独自管理、老人和家属共同管理、家属代为管理三类场景。首轮功能设计重点关注日常用药任务：帮助用户看清用药安排、按时完成服药、留下记录，并在漏服、重复服药、身体不适或药品不足时找到解决入口。

## 重点功能汇总

|优先级|功能模块|表现形式|
|---|---|---|
|首轮|药品清单与用药计划|药品清单、每日计划；录入后提供核对与修改入口，避免识别或输入错误直接形成提醒。|
|首轮|今日服药任务|以“现在该吃什么、吃多少、是否已经吃过”为主信息，减少其余信息对首屏的占用。|
|首轮|提醒与服药确认|提醒卡片、药品与剂量核对、二次确认、明确的成功反馈和可查看的服药记录。|
|首轮|漏服、重复服药与异常反馈|异常类型选择、事件记录、联系入口；页面不自行判断是否补服或调整剂量。|
|首轮|家属协作|老人端与家属端的任务边界、状态同步。|

|优化|药品余量与补药提醒|在药品详情与家属协作流程中预留余量和补药状态；提醒时间与余量计算方式需在原型阶段检查。|
|优化|用药咨询与线下服务衔接|一键联系和信息整理入口|
|优化|语音输入与知识内容|录入或搜索栏设置语音输入；知识内容置于次级页面，避免干扰当天服药任务。|

## 首轮 UI 的页面与任务流程

**老人用药基本任务流程为：**

> 建立并核对药品清单与计划 → 查看今日待服药物 → 收到提醒并核对药品、剂量 → 确认实际服药结果 → 查看记录；发生漏服、疑似重复服药或不适时，记录异常并联系家属或专业人员。
> 
> 

补药流程从药品余量进入，连接补药提醒和家属协助；专业咨询流程从异常记录或药品详情进入，便于带着清单和记录沟通。上述流程可直接用于绘制信息架构、关键页面和交互状态，后续再用原型可用性测试检查理解难度、误操作及任务完成情况。
